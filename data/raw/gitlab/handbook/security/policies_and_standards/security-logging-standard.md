## Summary

The GitLab Security Logging Standard defines how security-relevant events must be captured, structured, and retained across GitLab's product and infrastructure. Its goals are to enable threat detection, support security incident investigations, and ensure consistent, reliable log coverage across GitLab.com, GitLab Dedicated, and self-managed deployments.

### Guiding principles

- **Detection-first** - Log what is needed to detect meaningful threats such as account takeover, privilege escalation, data exfiltration, and CI/CD abuse.
- **Investigatability** - Logs must answer who did what, when, from where, to what, and with what outcome.
- **Consistency** - Event types, field names, and semantics must be uniform across product areas to support correlation and detection.
- **Privacy and least data** - Log only what is required for security; avoid credentials, secrets, and unnecessary personal data.
- **Reliability** - Critical security events must not be silently dropped; logging must be resilient to failure.
- **Cost-awareness** - Prefer low-volume, high-value events with standard fields.

### Event categories

Product teams must ensure the following categories of security-relevant events are logged as structured events:

- Authentication events (login, logout, MFA challenges, SSO login, failed logins)
- Session lifecycle events (session creation, refresh, termination)
- Authorization and privilege changes (role changes, permission changes, policy changes)
- Account lifecycle events (account creation, deactivation, deletion, password or email changes, MFA enrollment)
- Token and key lifecycle (personal access tokens, OAuth tokens, CI tokens, SSH keys, deploy keys: created, rotated, revoked)
- Project, repository, and code events (project creation or deletion, pushes, force pushes, protected branch changes, merge request approvals)
- CI/CD pipeline and job events (pipeline creation and approval, manual triggers, runner registration)
- Data access and export events (bulk downloads, repository clones, exports of membership lists or security reports)
- Configuration and admin events (changes to SSO, two-factor authentication policies, IP restrictions, webhooks, integrations)
- Security control and detection events (rate-limit blocks, abuse detection, policy violations)
- API usage events (security-sensitive API operations: admin actions, token management, configuration changes)
- Background and system actions (automated revocations, account locks, scheduled cleanups)

### Common required fields

All security events must be structured (JSON) and include at minimum:

- Event type and entity type
- UTC timestamp (ISO-8601)
- Unique event identifier
- Actor identifier and username
- Source IP address
- Target resource identifier, type, and details
- Outcome (success, failure, or unknown)

### Data protection

Security logs must never contain passwords, password hashes, tokens, secrets, or private keys. Where identifiers are needed, use hashes, fingerprints, or truncated values. Additional context logged for operational purposes must be scoped, redacted, and subject to restricted retention and access controls.

### Log format and transport

Security events must be logged in a structured format (JSON) with stable field names. All security events must use UTC timestamps. For GitLab-managed environments (GitLab.com, Dedicated), logs must be forwarded to the security logging platform and SIEM. For self-managed deployments, logs must be accessible and compatible with standard log shippers so customers can export to their own SIEM.

## Purpose and Scope

The purpose of this security logging standard is to define GitLab's requirements for security logging. This document covers both security logging in GitLab's SIEM (Devo) as well as security logging requirements for systems not sending logs to GitLab's SIEM.

## Roles & Responsibilities

| Role | Responsibility |
|------|----------------|
| GitLab System Owners (as defined in GitLab's tech stack) | Directly Responsible for adhering to the requirements outlined in this standard |
| Security Operations Team | Directly Responsible for the prioritization, onboarding and maintenance of logs in the Security team's SIEM (Security Information Event Management) system, Devo. |

## Security Logging Requirements

Security logs are generated by applications and systems used on GitLab and are primarily used for security monitoring, security incident response and cyber threat hunting.

The GitLab Security Operations team iteratively evaluates the priority of security logs for existing systems, and evaluates requests for new log sources that must be onboarded for improved security observability. The Security Operations team maintains a Single Source of Truth (SSOT) for the security logs in their SIEM.

As new applications, systems and services are onboarded at GitLab, if a system's security logs (e.g. App, OS, transaction logs) are not sent to GitLab's SIEM, security logs must be stored in approved secure storage for a duration aligned with our retention policy.

### Security Log Retention Requirements

| Security Log Description | Retention Requirements |
|--------|-------------|
| Security logs for production systems | 1 year minimum |
| Security logs for critical systems that are not production | 90 days minimum |

### Security Log Collection Requirements

At a minimum, authentication and transaction events must be collected for GitLab production systems and also for non-production critical GitLab systems.
